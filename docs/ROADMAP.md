# 云笔记 · 路线图

> 基于 V0.1 重排 · 2026-10-26

## 这一版改了什么

V0.1 的落地顺序有个隐患：它把「功能」排在了「基建」前面。分享入口、双链、CI 都在假设一件事——写进去的东西一定存得住、读得到。而实际遇到的第一个问题是「直接退出并不会保存」。

所以 V0.2 把顺序倒过来：**先保证存得住，再保证记得快，最后才是整理和回看。**

同时补了 6 条 V0.1 没覆盖的，修了 5 个已发现的缺口。

---

## 先说判断

三层架构成立：手机捕获、GitHub 存储、DeepSeek 加工。缺的是闭环。

**闭环有两层。** 第一层是「存进去的会回来看你」，V0.1 讲的是这个。第二层是「存的时候一定存得住」，V0.1 没讲。第二层不成立，第一层是空的。

---

## 一、先修已发现的缺口

这五条不是新功能，是承诺了但没兑现、或者已经踩到的坑。

| # | 问题 | 性质 |
|---|---|---|
| 1 | AI 助手页退出即清空，没有对话历史 | 功能缺失 |
| 2 | 主页「最近项目」应改成「最近打开的三个」 | 语义错位 |
| 3 | 热力图没做 | 承诺未兑现 |
| 4 | 直接退出不保存 | **架构问题，优先修** |
| 5 | 图片只能内嵌，应支持从文件管理器选图 + 压缩 | 捕获能力缺失 |

第 4 条单独说。现在保存是同步打 GitHub API，弱网、切后台、锁屏都会失败，失败还不落地——想法就这么没了。这不是加个 try-catch 能解决的，得改成写入本地立刻返回、后台队列重试、UI 上给「待同步」小点。这条是整个改造的地基。

---

## 二、基建层（优先级最高）

**1. 本地优先 + 发送队列**
写本地 SQLite 立即返回 → 队列异步同步 → 失败重试 → 状态可见。捕获成本再低，存不进去等于零。

**2. 增量同步**
现在每次拉全量 md。GitHub API 支持 `since` 参数和 ETag，只拉变更。200 条还行，2000 条会明显卡。

**3. 本地全文索引**
启动时缓存全部 md 到内存/轻量索引，搜索毫秒级返回。跟热力图是同一份数据源。

这三条不改任何交互，纯基建，但决定了后面所有功能的天花板。

---

## 三、捕获层

保留：系统分享（`intent-filter SEND`）、桌面快捷方式、无标题保存。补两条：

**4. 语音输入**
真实场景是走路、排队、洗完澡，前三项都在解决「打字更快」，没解决「不方便打字」。Android 系统 `SpeechRecognizer` 免费，几十行接上，录完直接进 `#raw`。这是捕获成本最低的一环，比分享入口更值。

**5. 图片附件 + 压缩**
从文件管理器选图，长边压到 1600px、JPEG q=80 再上传，原图不进仓库。笔记里图片数量会失控，不压缩等于把 GitHub 当网盘。

**6. 来源留存**
分享进来的条目要带 URL 和原文摘录（`来源: <url>` + 一段 quote）。想法几乎都有触发源，丢了出处，半年后自己都看不懂当时在说什么。

---

## 四、组织层

双链、状态标签、冲突双留原样保留。补一条依赖关系：**双链和反向链接依赖本地索引**，所以必须在基建之后。

冲突双留值得再强调：让用户在手机上做三选一，是把模型的活丢给人。

---

## 五、AI 层

**1. GitHub Actions 自动整理**
每天跑，生成回顾、待办、聚类，自动提交。

**2. 主动推送，不只是生成文件**
每周生成 `回顾/2026-W43.md` 还是「等你打开」。再加一层：Actions 挑一条（一年前的今天 / 躺了两周的 `#raw`），写进 `_push/next.md`，app 启动时读到就用本地通知弹出来。这才是「写下的东西回来看你」真正落地的那一下。

**3. 对话历史也进仓库**
`Deepseek/对话/2026-10-26.md`。AI 助手退出不清空，对话本身变成可检索素材，下次 DeepSeek 能读到自己之前说过什么。这条同时解决缺口 #1。

**4. 语义搜索放 CI 里算**（暂缓）
在 Actions 里把全仓库算成 embedding，存 `index.json` 提交回仓库，app 拉下来本地余弦匹配——离线、零成本。但索引文件随条目线性变大。**不到 500 条不用做**。

---

## 六、硬件方向（新）

**ESP32-S3 与桌面摆件**
把笔记的一小块能力放到桌面上：一块小屏循环显示最近的 `#raw` 或今日回顾，按键一下开始录音、录完自动进仓库。

这条跟主线是互补的：手机解决「随时记」，摆件解决「抬头就能看见」。技术上不冲突——ESP32-S3 走 HTTPS 打 GitHub API，和 app 用同一套 Contents 接口。

前提是先把 A 类的 token 下发方式想清楚（设备上不能存长期令牌），所以排在后续批次。

---

## 七、不建议做

系统悬浮球、app 内置 AI 对话、富文本编辑器。理由：权限过重、手机端没有本地模型、会毁掉 Markdown 的可移植性。

---

## 八、落地顺序

原则：每一批做完都能独立验证，且不阻塞下一批。

| 批次 | 内容 | 依赖 | 预估 |
|---|---|---|---|
| **0 · 止血** | 本地优先写入 + 失败队列<br>对话历史落仓库（缺口 1）<br>最近打开三个（缺口 2） | 无 | 1 天 |
| **1 · 基建** | 增量同步（since + ETag）<br>本地全文索引<br>图片附件 + 压缩（缺口 5）<br>热力图（缺口 3） | 批次 0 | 1.5 天 |
| **2 · 捕获** | 系统分享 SEND<br>桌面快捷方式<br>无标题保存<br>语音输入<br>来源留存 | 批次 0 | 1 天 |
| **3 · 组织** | `[[双链]]` + 反向链接<br>状态标签状态机<br>冲突双留 | 批次 1 | 1.5 天 |
| **4 · 自动化** | Actions 日报/周报<br>待办抽取、相似聚类<br>主动推送 | 批次 3 | 1.5 天 |
| **5 · 打磨** | diff 时光机<br>模板<br>（embedding 视条目数决定） | 批次 1 | 1 天 |
| **6 · 摆件** | ESP32-S3 桌面显示 + 语音录入 | 批次 2 | 待定 |

跟 V0.1 的关键差异：热力图从最后一批提到批次 1——它依赖索引，索引做完顺手就画，50 行 Canvas，没必要拖到最后。

---

## 最后一句

护城河是「手机 + 仓库 + 模型」这个闭环。

**闭环的第一环不是「捕获」，是「写进去了就真的在」。** 这一环不牢，后面全是表演。
